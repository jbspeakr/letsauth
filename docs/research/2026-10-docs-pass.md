# Documentation pass, October 2026

A read of each OAuth-listed server's public documentation, recorded as `vendor-claim` observations
dated 2026-10-14. Only documentation pages were read; no MCP server or authorization server was
contacted. Cells the docs do not address stay `unknown`. The table keeps the page each server's
auth model was taken from, for the Scanner (roadmap 004) to verify later.

| Server | Findings | Auth model per the docs | Source |
|---|---|---|---|

| asana | 7 | OAuth via Asana's own authorization server; DCR explicitly not supported, client developer must pre-register an 'MCP app' in the developer console for a client id and secret; PRM and AS metadata URLs documented. | [docs](https://developers.asana.com/docs/integrating-with-asanas-mcp-server) |
| atlassian | 0 | OAuth 2.1 via Atlassian's authorization server with an interactive consent screen; API-token authentication as an admin-enabled alternative. | attio | 0 | OAuth sign-in with the user's Attio account ('no API keys required'); docs name no registration mechanism and make no PKCE or metadata statements. | [docs](https://docs.attio.com/mcp/overview) |
| box | 4 | OAuth 2.0 via Box's authorization server; client ID and secret are generated by an admin in the Box Admin Console integration credentials (or a Developer Console app) and entered in the MCP client; no DCR statement; PRM and AS metadata URLs documented in Box's own README. | [docs](https://developer.box.com/guides/box-mcp/remote/) |

| canva | 3 | OAuth via Canva's authorization server; Client ID Metadata Documents (client_id as HTTPS URL) supported, DCR deprecated but still available; alternatively a pre-registered Developer Portal app with client ID and secret. | [docs](https://www.canva.dev/docs/apps/mcp/access/) |
| clickup | 2 | OAuth only (personal API keys and access tokens are rejected); custom clients must support OAuth 2.1 with PKCE; the Copilot Studio setup instructs 'Dynamic Discovery (DCR)' but DCR is not otherwise described | [docs](https://developer.clickup.com/docs/connect-an-ai-assistant-to-clickups-mcp-server) |
| cloudflare-workers | 0 | Cloudflare OAuth built in: interactive flow redirects to Cloudflare to authorize and pick permissions; a Cloudflare API token (user or account token) as a bearer in the Authorization header is the documented alternative for automation; no registration, PKCE or discovery details in docs | [docs](https://developers.cloudflare.com/agents/model-context-protocol/cloudflare/servers-for-cloudflare/) |
| cloudinary | 0 | Hosted remote servers use OAuth2 by default; API key/secret can be sent via request headers instead; no registration, PKCE or discovery details in docs | [docs](https://github.com/cloudinary/mcp-servers) |

| github | 2 | OAuth 2.1 + PKCE for hosts that have registered their own GitHub App or OAuth App (first-party Copilot IDEs and Cursor); any other host uses a PAT as a bearer token in the Authorization header; DCR not mentioned | [docs](https://github.com/github/github-mcp-server) |
| intercom | 2 | OAuth proxy in front of Intercom's own OAuth: DCR offered with a redirect-URI allowlist (localhost allowed on any port, other callbacks need a support-granted entry), server shows its own consent page then Intercom's authorization screen; Intercom API bearer tokens also accepted | [docs](https://developers.intercom.com/docs/guides/mcp) |
| linear | 1 | OAuth 2.1 with dynamic client registration via Linear's hosted server (follows the authenticated remote MCP spec); OAuth tokens from an existing Linear OAuth application or Linear API keys can also be passed directly as a bearer; requesting only the read scope yields read-only tokens | [docs](https://linear.app/docs/mcp) |
| miro | 0 | Browser OAuth flow against Miro (docs call it 'the base OAuth 2.1 authorization flow'), team-scoped, with optional OIDC id_token; client registration mechanism not named (FAQ only says clients 're-request a new Client ID from the MCP Server'), no metadata/PKCE/DCR statements. | [docs](https://developers.miro.com/docs/connecting-to-miro-mcp) |
| monday-com | 6 | OAuth 2.0 authorization code + PKCE via mcp.monday.com acting as authorization server (monday.com as identity provider); DCR supported with account-admin approval of connectors, or a manually created monday OAuth app (client ID/secret) as pre-registration path. | [docs](https://developer.monday.com/api-reference/docs/mcp-dynamic-client-registration) |
| neon | 2 | OAuth via Neon's hosted remote server (mcp.neon.tech), which is a proxy with its own authorization/token endpoints, .well-known discovery metadata and its own consent page (scopes read/write, 'Allow writes' checkbox) in front of Neon's upstream OAuth; API key in the Authorization header also accepted. | netlify | 0 | No vendor documentation of the remote server's authentication; docs.netlify.com/welcome/build-with-ai/netlify-mcp-server and the github.com/netlify/netlify-mcp README only give the URL https://netlify-mcp.netlify.app/mcp and a Personal Access Token fallback for the local npx server. | none found |
| notion | 8 | OAuth 2.1 via Notion's own authorization server discovered through PRM at mcp.notion.com; DCR (RFC 7591) and CIMD supported, PKCE S256 required but not advertised per the guide, refresh tokens rotated on every refresh. | [docs](https://developers.notion.com/guides/mcp/build-mcp-client) |
| paypal | 0 | Docs describe connecting via mcp-remote with 'PayPal client credentials' (the account's REST app client ID and secret from the Developer Dashboard) passed as an Authorization: Bearer header, plus a PayPal login page where the user authorizes the client; no OAuth 2.1, DCR, PKCE or metadata statements. | [docs](https://developer.paypal.com/tools/mcp-server/) |
| plaid | 1 | OAuth 2.0 client_credentials grant against Plaid's /oauth/token with the team's client ID and Production secret and scope mcp:dashboard; short-lived (15 min) access tokens with refresh tokens; no user authorization flow, no DCR, PKCE or metadata statements. | [docs](https://plaid.com/docs/resources/mcp/) |
| prisma-postgres | 0 | OAuth-style sign-in with a Prisma account via the Prisma Console authorization flow ('Connect from an AI tool that supports remote MCP servers with OAuth sign-in'); docs, blog and changelog do not describe the mechanics (no DCR, PKCE, metadata or client-registration statements). | [docs](https://www.prisma.io/docs/ai/tools/mcp-server) |
| ramp | 0 | OAuth sign-in with the user's Ramp account; any remote-MCP client that supports OAuth can connect, but clients with a hosted redirect URL must have it allowlisted by Ramp. | square | 1 | OAuth login with the user's Square account on the remote server (production resources only); MCP client registration is gated by a Square-maintained allowlist, with redirect domains added on request in the Square developer forum; DCR mechanics, PKCE and metadata are not described. | [docs](https://developer.squareup.com/docs/mcp) |

## Not recorded

- Figma, Vercel and Square restrict connections to allowlisted clients; only the documented registration path was recorded, not a guess at the mechanism.
- PayPal and Plaid document machine credentials (the account's own client ID and secret) rather than a user authorization flow; noted on the server files.
- Pages that only say "sign in with OAuth" (Atlassian, Attio, Buildkite, Cloudflare, Cloudinary, Miro, Prisma, Ramp, Stack Overflow, Stripe, Todoist, Webflow, Wix) yielded no feature-level statement. Netlify has no authentication documentation for its remote server.
